```bash
./status.sh
```

```bash
curl http://127.0.0.1:8077/api/health
```

## Быстрая таблица

| Симптом | Причина | Что делать |
|---|---|---|
| `Docker установлен, но демон недоступен` | Docker Desktop не запущен | запустить Docker Desktop, дождаться зелёного статуса, повторить `./start.sh` |
| `Порт 8077 уже занят другим процессом` | висит старый uvicorn или чужой сервис | `./stop.sh`, либо `./start.sh --port 8078` |
| `Не удалось запустить docker compose` | заняты 13306 или 16379 | освободить порты или переопределить `TGV_MYSQL_PORT` / `TGV_REDIS_PORT` |
| `bash: ./start.sh: /usr/bin/env^M: bad interpreter` | файл сохранён с CRLF | `sed -i 's/\r$//' start.sh stop.sh status.sh` |
| `'.' is not recognized as an internal or external command` | скрипт запущен в `cmd.exe`/PowerShell | запускать из **Git Bash** |
| `MySQL не стал healthy` | повреждённый том или нехватка памяти | `dc logs mysql`, при необходимости `./start.sh --fresh` |
| `API_ID_INVALID` | неверная пара `api_id`/`api_hash` | перепроверить на my.telegram.org, `PATCH` аккаунт или создать заново |
| `PHONE_CODE_INVALID` | опечатка в коде | ввести код заново, состояние не потеряно |
| `PHONE_CODE_EXPIRED` | код протух | `POST /api/auth/{id}/phone/send-code` заново |
| `FLOOD_WAIT` с `retry_after` | лимит Telegram | ждать указанное число секунд, не ретраить в цикле |
| `PASSWORD_INVALID` | неверный облачный пароль | ввести заново; код/QR повторять не нужно |
| QR истёк до сканирования | токен живёт ~30 с | `POST /api/auth/{id}/qr/refresh` |
| `AUTH_KEY_UNREGISTERED` | сессия отозвана вручную или Telegram'ом | войти заново |
| `AuthKeyDuplicatedError` в логах | одна сессия использована из двух мест | остановить второй экземпляр, войти заново; `session_enc` уже обнулён |
| Задача навсегда в `queued` | планировщик не работает или занято 3 слота | проверить `/api/export/jobs?status=running`, посмотреть `app.log` |
| Файлы падают с `file reference expired` | нормальный износ ссылок на длинном экспорте | обычно движок чинит сам; если статус `failed` — перезапустить экспорт |
| `No space left on device` | кончилось место | освободить диск, перезапустить задачу — уже скачанное пропустится |
| UI показывает JSON `{"app":"TgVault","ui":"не собран"}` | нет `frontend/dist` | `./start.sh --rebuild` или `cd frontend && npm run build` |
| WebSocket не подключается | backend перезапущен или прокси разорвал сокет | клиент должен переподключаться с backoff и перечитать состояние по REST |

## Docker и порты

### Docker не запущен

`start.sh` останавливается на шаге проверки окружения:

```
[err] Docker установлен, но демон недоступен.
```

Windows/macOS: запустить Docker Desktop и дождаться, пока значок станет зелёным.
Linux: `sudo systemctl start docker`.

Если MySQL и Redis подняты отдельно (не через docker):

```bash
./start.sh --no-docker
```

### Порт занят

TgVault использует четыре нестандартных порта:

| Порт | Сервис | Кто занял? |
|---|---|---|
| `8077` | backend (uvicorn) | предыдущий запуск TgVault |
| `5177` | Vite dev-сервер | предыдущий `--dev` |
| `13306` | MySQL в контейнере | другой compose-проект |
| `16379` | Redis в контейнере | другой compose-проект |

Кто держит порт:

```bash
netstat -ano | grep ':8077'
```

```powershell
Get-NetTCPConnection -LocalPort 8077 | Select-Object OwningProcess, State
```

Штатный способ освободить всё:

```bash
./stop.sh
```

Разовый обход для backend:

```bash
./start.sh --port 8078
```

Постоянный — поменять в `.env` `TGV_PORT`, `TGV_FRONTEND_PORT`, `TGV_MYSQL_PORT`,
`TGV_REDIS_PORT` (последняя читается только `docker-compose.yml`).

> Если `start.sh` пишет «backend уже работает и здоров (pid N) — переиспользую», это не ошибка:
> скрипт нашёл живой процесс с отвечающим `/api/health` и не стал его трогать.
> Принудительный перезапуск: `./start.sh --rebuild` или сначала `./stop.sh`.

## Windows: скрипты не запускаются

### `bad interpreter: /usr/bin/env^M`

Файл сохранён с окончаниями строк CRLF (обычно из-за `core.autocrlf=true` в git).

```bash
sed -i 's/\r$//' start.sh stop.sh status.sh
```

Чтобы не повторялось:

```bash
git config core.autocrlf input
```

Внутри самих скриптов чтение `.env` уже устойчиво к CRLF — проблема только в самих `.sh`.

### Запуск не из Git Bash

`cmd.exe` и PowerShell не умеют выполнять `./start.sh`. Git Bash входит в состав
[Git for Windows](https://git-scm.com/download/win). Правый клик в папке проекта →
**Git Bash Here** → `./start.sh`.

WSL тоже работает, но тогда Docker Desktop должен иметь включённую WSL-интеграцию, а пути
к данным будут внутри WSL-файловой системы.

### `permission denied: ./start.sh`

```bash
chmod +x start.sh stop.sh status.sh
```

## MySQL

### Контейнер не становится healthy

`start.sh` ждёт до 120 секунд и печатает последние 40 строк лога контейнера. Посмотреть больше:

```bash
docker compose --env-file .env -f docker/docker-compose.yml logs --tail=200 mysql
```

Частые причины:

| В логе | Причина | Решение |
|---|---|---|
| `[ERROR] ... Data Dictionary initialization failed` | том повреждён (жёсткое выключение) | `./start.sh --fresh` — тома пересоздаются, **база теряется** |
| `Another process with pid N is using unix socket file` | контейнер не остановился корректно | `docker rm -f tgvault-mysql`, затем `./start.sh` |
| `mbind: Operation not permitted` | безобидное предупреждение | игнорировать |
| зависает на `InnoDB: Initializing buffer pool` | мало памяти у Docker | увеличить лимит памяти Docker Desktop или снизить `--innodb-buffer-pool-size` в `docker/docker-compose.yml` |
| `Access denied for user 'tgvault'` | пароль в `.env` разошёлся с тем, что записан в томе | либо вернуть старый пароль, либо `./start.sh --fresh` |

Важно: `MYSQL_USER`/`MYSQL_PASSWORD` применяются **только при первичной инициализации тома**.
Смена пароля в `.env` на существующем томе ничего не изменит внутри MySQL.

### Backend не дожидается базы

```
MySQL at 127.0.0.1:13306 is not reachable after 90s. Is Docker running?
```

`wait_for_database()` перепробовал подключение в течение 90 секунд. Проверить руками:

```bash
docker exec tgvault-mysql mysqladmin ping -h 127.0.0.1 --silent
```

Если контейнер жив, а порт не отвечает — вероятно конфликт проброса портов. Проверить:

```bash
docker port tgvault-mysql
```

### Не удалось удалить старый FULLTEXT-индекс

В `app.log` появляется:

```
WARNING [tgvault.db] Could not drop the FULLTEXT index: ...
```

Приложение продолжит работать — индекс не используется, он только замедляет вставку при
больших экспортах. Чтобы всё-таки убрать его, выдайте пользователю права `ALTER`/`INDEX`
на базу либо удалите вручную:

```bash
docker exec tgvault-mysql mysql -utgvault -ptgvault -D tgvault -e "DROP INDEX ft_messages_text ON messages;"
```

## Авторизация

### `API_ID_INVALID`

Пара `api_id`/`api_hash` не совпадает или введена с опечаткой.

* `api_id` — число (7-8 цифр), `api_hash` — ровно 32 hex-символа;
* перепроверить на <https://my.telegram.org> → **API development tools**;
* `api_hash` изменить через API нельзя — только `label` и `proxy`. Проще удалить аккаунт
  (`DELETE /api/accounts/{id}`) и создать заново;
* убедиться, что не используется `api_id` из чужого репозитория или туториала: публично
  засвеченные пары постоянно тротлятся сервером.

### `PHONE_CODE_INVALID` и `PHONE_CODE_EXPIRED`

* `PHONE_CODE_INVALID` — код неверен. Backend сам вырезает пробелы и дефисы, так что дело
  в цифрах. Введите заново, повторно запрашивать код не нужно.
* `PHONE_CODE_EXPIRED` — код протух. Нужен новый: `POST /api/auth/{id}/phone/send-code`.
* Если кодов подряд запрошено много, следующий запрос упрётся в `FLOOD_WAIT`:
  `auth.sendCode` ограничен примерно 5 попытками в сутки на номер.
* Иногда Telegram присылает код не в приложение, а SMS-ом. Тип видно в `AuthState.code_type`.

### `FLOOD_WAIT`

Тело ошибки содержит точное число секунд:

```json
{ "detail": "Telegram временно ограничил попытки. Повторите через 86400 с.",
  "code": "FLOOD_WAIT", "retry_after": 86400 }
```

**Ждать нужно ровно столько.** Никакой обход не работает: ни смена IP, ни новый `api_id`,
ни перезапуск приложения — счётчик на стороне сервера, привязан к аккаунту и типу запроса.
Автоматические ретраи только продлевают ожидание.

Типичные значения: десятки секунд для истории сообщений, часы для повторных попыток входа,
86400 с (сутки) — для `auth.sendCode` при переборе.

Во время экспорта FloodWait — норма: ожидания короче `TGV_FLOOD_SLEEP_THRESHOLD` (60 с) Telethon
отсыпает молча, длинные видно в таймлайне задачи как «Ограничение Telegram (FloodWait): пауза N с».
Ожидание дольше 3600 с останавливает задачу с ошибкой — её можно просто перезапустить позже,
инкрементальный режим не даст качать заново.

### Пароль 2FA не принимается

`PASSWORD_INVALID` означает буквально неверный пароль — это **облачный пароль Telegram**
(тот, что задан в Настройки → Конфиденциальность → Облачный пароль), а не код из SMS и не
пароль от компьютера. Подсказку, если она задана, backend отдаёт в `AuthState.password_hint`.

Состояние остаётся `password_required`: повторять код или QR не нужно, можно сразу пробовать
ещё раз. Если пароль забыт — сбрасывать его придётся через официальный клиент Telegram
(процедура сброса занимает 7 дней).

Если пароля вообще не должно быть, а его спрашивают — значит 2FA включён на аккаунте. Проверьте
в мобильном клиенте.

### QR истекает раньше, чем успеваешь отсканировать

Токен живёт примерно 30 секунд (точное значение приходит с сервера и отдаётся в
`qr_expires_at` — не полагайтесь на константу).

* `POST /api/auth/{id}/qr/refresh` — новый токен на том же клиенте и том же DC;
* если объект `QRLogin` потерян (backend перезапускался) — `refresh` прозрачно сделает `qr/start`;
* заранее откройте на телефоне **Настройки → Устройства → Подключить устройство**, и только
  потом смотрите на экран;
* после успешного сканирования может появиться запрос облачного пароля — это нормально.

Если после сканирования ничего не происходит: ожидание должно было работать в момент
сканирования. Backend запускает его сразу в `qr/start`, но если между `qr/start` и сканированием
процесс перезапускался — токен «повис». Нажмите обновление QR и отсканируйте новый.

### `AuthKeyUnregisteredError` / `AUTH_KEY_UNREGISTERED`

Сессия больше не действительна: её отозвали вручную (Настройки → Устройства → завершить сеанс),
либо это сделал Telegram. Лечится только повторным входом. Аккаунт переходит в `unauthorized`,
архив в базе остаётся целым.

### `AuthKeyDuplicatedError` — самое неприятное

Telegram уничтожает ключ авторизации, когда обнаруживает, что **одна и та же сессия шлёт запросы
параллельно с двух разных TCP-соединений** на не-медийный DC. Это не FloodWait и не временная
мера: ключ уже уничтожен на сервере.

Что делает TgVault: переводит аккаунт в `unauthorized`, пишет причину в `last_error`,
**обнуляет `session_enc`**, отключает клиента и завершает задачу статусом `failed`.

Что делать: войти заново (QR или код) и устранить причину.

**Причины, в порядке частоты:**

1. Запущено две копии TgVault на одной базе (или один экземпляр через `start.sh`, второй руками
   через `uvicorn`). Проверить: `./status.sh`, `ps aux | grep uvicorn`.
2. Та же строка сессии скопирована в другой инструмент (свой скрипт, tdl, telegram-export).
3. Строка сессии восстановлена из бэкапа и используется параллельно с «живой».
4. Очень высокий `concurrency` в опциях экспорта. Значения выше 8 не дают выигрыша (Telethon
   всё равно мультиплексирует запросы по одному соединению на DC), но повышают риск.

> **Правило:** одна строка сессии — одно живое подключение в один момент времени.
> Переносить сессию между машинами можно, но подключаться из двух мест сразу — нельзя.

## Экспорт

### Задача навсегда в `queued`

Проверить по порядку:

1. **Заняты все слоты.** Одновременно выполняется не больше 3 задач:

```bash
curl 'http://127.0.0.1:8077/api/export/jobs?status=running'
```

2. **Планировщик не запустился.** В `data/logs/app.log` при старте должна быть строка
   `Export scheduler started (max 3 concurrent jobs)`. Если её нет — backend не прошёл lifespan
   до конца, ищите ошибку выше по логу.

```bash
curl 'http://127.0.0.1:8077/api/logs?search=scheduler&limit=20'
```

3. **Задача упала сразу после старта и была возвращена в очередь.** Посмотрите её таймлайн:

```bash
curl http://127.0.0.1:8077/api/export/jobs/12/events
```

4. **Аккаунт разлогинился.** Движок на старте проверяет `is_user_authorized()`; при провале
   задача уйдёт в `failed` с текстом «Аккаунт не авторизован — войдите заново».

Планировщик проверяет очередь раз в 1.5 секунды, так что нормальная задержка старта — секунды,
а не минуты.

### Задача сразу `failed` с «Не удалось получить доступ к чату»

Движок пробует резолвить чат по `tg_chat_id`, затем по `username`, через `get_entity` и
`get_input_entity`. Если все четыре попытки провалились:

* аккаунт вышел из канала/группы — вернитесь в него;
* канал приватный, а инвайт-ссылка была одноразовой;
* список чатов устарел (`access_hash` протух) — выполните синхронизацию чатов заново:
  `POST /api/accounts/{id}/chats/sync`.

### Файлы падают с `file reference expired`

Штатная ситуация на длинных экспортах: ссылка на файл, полученная вместе с сообщением, живёт
несколько часов. Движок перезапрашивает сообщение (`get_messages(ids=…)`) и повторяет загрузку
со свежей ссылкой — обычно это невидимо.

Если файл всё же ушёл в `failed`:

```sql
SELECT id, tg_message_id, kind, attempts, LEFT(error, 120) AS error
FROM media_files WHERE status = 'failed' AND chat_id = 5;
```

Просто запустите экспорт этого чата ещё раз. Инкрементальный режим и `skip_existing` не дадут
качать заново то, что уже скачано; проваленные файлы получат новую попытку.
Если сообщение удалено в Telegram — файл не восстановить, это ожидаемо.

### Кончилось место на диске

Симптомы: файлы массово в `failed` с `OSError: [Errno 28] No space left on device` или
`[WinError 112]`; в `error.log` — исключения при записи.

1. Освободить место или перенести `TGV_DATA_DIR` на другой диск (в `.env` можно указать
   абсолютный путь, например `TGV_DATA_DIR=D:/tgvault-data`).
2. Оценить, сколько потребуется, до запуска:

```sql
SELECT ROUND(SUM(size)/1024/1024/1024, 1) AS gb
FROM media_files WHERE chat_id = 5;
```

3. Ограничить объём опциями: `max_file_size_mb`, сузить `media_types`, задать `date_from`,
   или вовсе `download_media: false` для текстового архива.
4. Перезапустить задачу — скачанное пропустится.

Место занимают ещё и docker-тома. Посмотреть:

```bash
docker system df -v
```

### Экспорт идёт, но очень медленно

* Реалистичная скорость одного соединения Telethon — 0.3–0.5 МБ/с без `cryptg` и 1–2 МБ/с с ним.
  Установка `cryptg` в venv обычно даёт больший выигрыш, чем любые настройки:

```bash
backend/.venv/bin/pip install cryptg
```

* `concurrency` выше 8 практически не помогает: Telethon мультиплексирует запросы по одному
  соединению на DC — зато растёт риск `AuthKeyDuplicatedError`.
* Telegram Premium снимает серверный лимит скорости, но узкое место здесь не в нём.
* Проверьте, не сидит ли задача в FloodWait: `GET /api/export/jobs/{id}/events`.

### Задача «зависла» на паузе после перезапуска

Так и задумано: при старте приложения все задачи в статусах `running` и `paused` переводятся
в `queued` с событием «Приложение было перезапущено — задача возвращена в очередь».
Восстановление паузы между процессами не поддерживается — объект `JobControl` живёт только
в памяти. Задача просто запустится заново и пропустит уже сделанное.

## Интерфейс и WebSocket

### Вместо UI отдаётся JSON

```json
{ "app": "TgVault", "version": "1.0.0", "ui": "не собран — запустите ./start.sh или frontend: npm run build", "docs": "/docs" }
```

Нет файла `frontend/dist/index.html`.

```bash
./start.sh --rebuild
```

```bash
cd frontend && npm install && npm run build
```

Проверьте также, что `TGV_SERVE_FRONTEND` не выставлен в `false`.
API и Swagger при этом работают: <http://127.0.0.1:8077/docs>.

### `npm install` или `npm run build` падает

`start.sh` не считает это фатальным — запуск продолжится в API-only режиме с предупреждением.
Смотреть подробности:

```bash
cd frontend && npm install --no-fund --no-audit
```

Радикально:

```bash
rm -rf frontend/node_modules frontend/package-lock.json && cd frontend && npm install
```

Проверьте версию Node: нужен ≥ 18 (`node -v`).

### Прогресс не обновляется, WebSocket отваливается

* Проверьте число подключённых клиентов: `curl http://127.0.0.1:8077/api/health` → `ws_clients`.
* Сервер шлёт heartbeat `{"type":"pong"}` каждые 25 секунд; если кадров нет больше минуты —
  соединение мертво, переподключайтесь.
* События при разрыве **не буферизуются**. После реконнекта перечитайте состояние по REST:
  `GET /api/export/jobs`, `GET /api/accounts`, `GET /api/export/jobs/{id}/events?after_id=…`.
* В dev-режиме за проксирование `/ws` отвечает Vite — при его перезапуске сокет рвётся.

### Redis недоступен

В `app.log`:

```
WARNING [tgvault.bus] Redis unavailable (...) — continuing without it
```

Это не ошибка: шина деградирует до in-process, WebSocket и прогресс продолжают работать.
Отключить попытки подключения совсем:

```bash
TGV_REDIS_ENABLED=false
```

## Логи

Все файлы — в `data/logs/`.

| Файл | Что внутри | Ротация |
|---|---|---|
| `app.log` | всё, от `DEBUG`, единый формат `дата уровень [логгер] сообщение` | 20 МБ × 7 |
| `error.log` | только `ERROR` и выше, со стектрейсами | 10 МБ × 5 |
| `telegram.log` | вывод Telethon от `INFO` — проблемы MTProto, реконнекты, флуды | 20 МБ × 3 |
| `backend.out.log` | stdout/stderr процесса uvicorn (пишет `start.sh`) | перезаписывается при старте |
| `frontend.out.log` | вывод Vite dev-сервера | перезаписывается при старте |

Следить в реальном времени:

```bash
tail -f data/logs/app.log
```

Только ошибки:

```bash
tail -n 200 data/logs/error.log
```

По конкретной задаче:

```bash
grep '\[job 12\]' data/logs/app.log
```

Всё то же доступно через API и UI (раздел «Логи»):

```bash
curl 'http://127.0.0.1:8077/api/logs?level=ERROR&limit=50'
```

```bash
curl 'http://127.0.0.1:8077/api/logs/files/telegram.log?tail=200'
```

Включить SQL-запросы в лог (шумно, только для отладки): `TGV_DB_ECHO=true` в `.env`.
Поднять детализацию консоли: `TGV_LOG_LEVEL=DEBUG`.

> В `app_logs` (таблице) автоочистки нет. Если таблица разрослась:
> `DELETE FROM app_logs WHERE ts < NOW() - INTERVAL 30 DAY;`

## Полный сброс

По возрастанию радикальности.

**1. Перезапустить приложение, БД не трогать:**

```bash
./stop.sh --keep-db && ./start.sh
```

**2. Перестроить зависимости и фронтенд:**

```bash
./start.sh --rebuild
```

**3. Снести базу целиком (тома docker), файлы экспорта оставить:**

```bash
./stop.sh --purge
```

Потребует ввести `yes`. Удаляет тома `tgvault_mysql_data` и `tgvault_redis_data`:
аккаунты, сессии, чаты, сообщения, метаданные файлов и история задач исчезают безвозвратно.
Содержимое `data/exports/` остаётся на диске.

То же самое на старте:

```bash
./start.sh --fresh
```

**4. Сброс до заводского состояния**, включая ключ шифрования и все выгрузки:

```bash
./stop.sh --purge
```

```bash
rm -rf data/ .env
```

После этого `./start.sh` создаст `.env` заново и сгенерирует новый `TGV_SECRET_KEY`.

> **Внимание:** удаление `data/secret.key` делает сохранённые сессии нерасшифровываемыми.
> Если база при этом уцелела, аккаунты просто перейдут в состояние, требующее повторного
> входа — данные архива не пострадают.

Перед любым сбросом стоит снять дамп (см. [SETUP §8](SETUP.md#8-где-лежат-данные-и-как-их-бэкапить)):

```bash
docker exec tgvault-mysql mysqldump -u tgvault -ptgvault --single-transaction --default-character-set=utf8mb4 tgvault > tgvault-backup.sql
```
