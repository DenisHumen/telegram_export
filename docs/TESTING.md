# Тестирование

В проекте два набора проверок. Оба запускаются одной командой, без pytest и
дополнительных зависимостей — только тем Python, который уже стоит в `backend/.venv`.

| Набор | Файл | Что проверяет | Нужен запущенный backend |
|---|---|---|---|
| Движок экспорта | `backend/tests/smoke.py` | извлечение сообщений, типы медиа, раскладка, загрузка, инкрементальность, синк чатов, пересборка, отмена | нет (нужен только MySQL) |
| API | `backend/tests/api_smoke.py` | все читающие эндпоинты, коды ошибок, обход каталога | да |

## Запуск

```bash
cd backend
.venv/Scripts/python -m tests.smoke
```

```bash
cd backend
.venv/Scripts/python -m tests.api_smoke
```

На Linux/macOS путь к интерпретатору — `.venv/bin/python`.
`api_smoke` принимает необязательный адрес: `python -m tests.api_smoke http://127.0.0.1:8077`.

Оба скрипта завершаются кодом `1` при первой непройденной проверке и печатают
итог вида `ВСЕ ПРОВЕРКИ ПРОЙДЕНЫ: 59`.

## Тестовая база

`tests/smoke.py` **не трогает рабочий архив**: до импорта `app.config` он
подменяет переменные окружения и работает с отдельной базой `tgvault_test`
и временным каталогом данных, который создаётся в системном temp.

```
TGV_MYSQL_DB=tgvault_test
TGV_REDIS_ENABLED=false
TGV_DATA_DIR=<временный каталог>
```

Базу нужно создать один раз (пользователю `tgvault` выдаются права на неё):

```bash
docker exec tgvault-mysql mysql -uroot -ptgvault_root -e "CREATE DATABASE IF NOT EXISTS tgvault_test CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci; GRANT ALL ON tgvault_test.* TO 'tgvault'@'%'; FLUSH PRIVILEGES;"
```

Каждый прогон выполняет `reset_db()` — схема пересоздаётся с нуля.

## Как устроен тест движка

Настоящий `TelegramClient` в тестах использовать нельзя: нужен номер телефона,
сеть и лимиты Telegram. При этом движок экспорта — как раз то, что важнее всего
проверять. Поэтому `tests/fakes.py` реализует ровно ту поверхность Telethon,
которой пользуется `ExportEngine`:

* `FakeMessage` — сообщение, у которого нужные медиа-свойства отвечают правдиво,
  **включая ловушки порядка**: кружочек (`video_note`) одновременно отвечает
  и на `.video`, видео-стикер — и на `.sticker`, и на `.video`, GIF — на `.gif`
  и `.video`. Если кто-то переставит проверки в `detect_media_type`, тест упадёт.
* `FakeClient` — `iter_messages`, `get_messages`, `download_media` (пишет файл
  нужного размера на диск), `iter_dialogs`, `get_entity`.
  Флаг `fail_first_download=True` имитирует обрыв сети на первом файле, чтобы
  проверить, что повтор отрабатывает.
* `build_dialogs()` строит **настоящие** объекты `telethon.tl.types.Channel`,
  `Chat`, `User`, потому что `dialogs.classify` различает их через `isinstance` —
  подделка молча ушла бы не в ту ветку.

Клиент подставляется в `TelegramManager` напрямую (`manager._handles`), после чего
`ExportEngine` работает так же, как в бою.

## Что именно покрыто

**Движок (`tests/smoke.py`)**

1. Определение типа медиа для 8 видов вложений + ловушки порядка.
2. Все 8 стратегий раскладки, шаблон имени файла, поведение при битом шаблоне,
   вычистка запрещённых в Windows символов.
3. Полный прогон экспорта: 12 сообщений, 10 файлов, повтор после сбоя сети,
   совпадение счётчиков задачи с содержимым БД.
4. Создание `manifest.json`, `messages.json/jsonl/csv/txt`, `index.html`,
   `assets/data.js` (и что это именно присваивание, иначе просмотрщик не
   откроется с `file://`).
5. Физическая раскладка файлов на диске.
6. Инкрементальный повтор: ничего не тянется заново, дублей в БД нет.
7. Синхронизация диалогов и классификация: broadcast → `channel`,
   megagroup → `supergroup`, обычный чат → `group`, пользователь → `user`,
   бот → `bot`. Повторный синк обновляет, а не дублирует.
8. Пересборка вывода из базы без обращения к Telegram.
9. Отмена задачи.

**API (`tests/api_smoke.py`)**

* `/api/health`, `/api/stats`, `/openapi.json`.
* Аккаунты: создание, чтение, переименование, удаление, ошибки 400/404.
* Список чатов во **всех** сочетаниях сортировки и фильтров — именно так был
  пойман баг с `NULLS LAST`, который MySQL не поддерживает (см. ниже).
* Авторизация: состояние, QR-статус, отмена, и что фиктивные `api_id`/`api_hash`
  честно превращаются в `API_ID_INVALID`.
* Логи: фильтры по уровню, аккаунту, задаче, поиску; список и чтение файлов.
* Попытки обхода каталога (`..%2F..%2F.env` и т. п.) — проверяется не код ответа,
  а то, что в теле нет `TGV_SECRET_KEY`, `TGV_MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`.

## Что эти тесты поймали

Не декоративные проверки — каждый из этих багов был найден именно ими:

| Баг | Симптом | Исправление |
|---|---|---|
| `NULLS LAST` в сортировке чатов | MySQL 1064 на **главном экране** — список чатов вообще не открывался | сортировка через `col IS NULL` (`services/chats.py`) |
| Коммит после отправки ответа | `POST /api/accounts` → 201, сразу `GET` → 404; `DELETE` → 200, сразу `GET` → 200 | `CommitRoute` в `api/deps.py` — коммит до возврата ответа |
| `socket_timeout` на pub/sub Redis | подписка отваливалась через 5 секунд простоя | отдельное соединение без таймаута + переподключение (`bus.py`) |
| Относительный `base` у Vite | белый экран на любом вложенном маршруте (`/accounts/new`) | `base: '/'` + 404 вместо HTML для отсутствующих ассетов |

## Чего тесты не покрывают

Эти пути требуют живого аккаунта Telegram и проверяются вручную:

* вход по коду и по QR до конца (успешный сценарий), ввод облачного пароля 2FA;
* реальные `FloodWait` и протухание `file_reference` на длинном экспорте;
* takeout-сессия;
* скачивание аватарок чатов.
